### B1. 审批框（权限请求卡片）**[已查明]**

**它是什么**：Agent 执行过程中要改文件、跑命令时会请求授权。这个框让你直接在灵动岛上
批准或拒绝，不用切回 Agent 的终端窗口。四个按钮分别是：拒绝 / 允许一次 /
始终允许（本次会话内该类操作不再问）/ 自动批准（后续全部自动放行）。

它不是装饰，按钮真的会把决定回传给 Agent（`respondPermission` → Hook 通道）。

**来历**：最初的 PRD 第 23 行写的是「**知道**哪些 Agent 正在等待权限或用户输入」——
要求的是**可见性**，不是在岛上直接批准。直接批准的交互是上游 AgentBro 带来的能力，
随 fork 保留至今，**确实没有被明确要求过**。

**存在必要性的论证**：
- 支持保留：它正面解决 PRD 里「不用切窗口」这个核心诉求。只显示「某某在等权限」
  而必须切窗口去点同意，等于把问题解决了一半。
- 支持去掉：它是弹出式的，会遮挡内容；而且截图里 Agent 名显示为 `Unknown`，
  说明会话标题没取到，观感像是坏的。

**已决策（2026-09-19）：不需要，移除。** 维护者不接受上面的折中方案。

**移除时必须保留的东西（需维护者确认边界）**：PRD 第 23 行要求的是
「知道哪些 Agent 正在等待权限或用户输入」。如果连同「某某在等权限」的状态提示

## C. Bug

### C1. 设置窗口最小化后无法恢复 **[已查明根因]**

**复现**：最小化设置面板后再也打不开。

**根因**（`src-tauri/src/lib.rs`）：
1. 第 2229 行 `window.set_skip_taskbar(true)` —— 设置窗口被刻意排除在 Windows
   任务栏之外，所以最小化后任务栏上没有可点的按钮。
2. `show_settings_window` 只调用了 `show()` 和 `set_focus()`，**全仓库没有任何
   `unminimize()` 或 `is_minimized()` 调用**。在 Windows 上对一个已最小化的窗口
   调 `show()` 不会还原它。

两者叠加 → 窗口既不在任务栏、也无法通过再次「打开设置」还原。

**补充根因**：设置窗口是**带原生标题栏**的（`build_settings_window` 未禁用装饰），
所以标题栏上有最小化按钮可点；而关闭按钮走的是「隐藏到托盘」而非最小化。
也就是说最小化是用户唯一能触发、且没有任何恢复入口的状态。

**已修复（2026-09-19，未真机验证）**：`show_settings_window` 在 `show()` 之前
增加 `is_minimized()` 判断与 `unminimize()` 调用，失败时写警告日志。
`cargo check --all-targets` 与 `cargo fmt --check` 通过。

**仍需维护者真机验证**：窗口最小化状态无法用单元测试覆盖。验证步骤——
打开设置 → 点标题栏最小化 → 从灵动岛再次打开设置 → 应当还原并获得焦点。

### E4. 「0 个 GitHub 来源可检查」是什么意思 **[已查明]**

**不是功能坏了。** 这个数字统计的是「来源为 GitHub 的 Skill 有几个」
（判据：`sourceType === 'github'` 或来源地址含 `github.com`）。

## F. 使用额度

### F1. 设置页里的额度展示看不懂 **[待设计]**

维护者反馈：灵动岛上的展示还行，设置里的看不懂每一块是干嘛的。

**已知背景**：这个页面 2026-09-18 刚调整过口径——原先的网络抓包采集随
Inspector 一起下线了，现在的数字来自「每个 Agent 最近一次会话」的 token 快照，
不是当天累计。文案已标注，但整个页面的信息层级没有重新设计过。

**已决策（2026-09-19）：这个页面是一个「记录仪表盘」，回答两个问题。**
1. **现在还剩多少额度。**
2. **额度结算**：某一天 / 某一周 / 某一月用了多少 token，按官方定价折算成金额。

凭据问题维护者的决定：**交给用户。用户批准后，就用用户的登录凭据去调 Provider 接口。**
（即 F2 里的路线 B。）

#### 这不是 UI 改版，是三个新子系统

按上面的目标，当前代码缺的不是布局，是数据。动手前必须认识到：

1. **没有历史数据。** 现在后端只保存「每个 Agent 最近一次会话」的 token 快照
   （`AgentStatusSnapshot.tokens` 是覆盖赋值，见 2026-09-18 的口径更正）。
   要回答「某天/某周/某月用了多少」，必须新建**按时间累积的用量历史存储**，
   而且要决定：保留多久、存在哪（沿用 `control_tower` 的 SQLite？）、
   旧数据从哪来（历史无法追溯，只能从启用之日起累积）。
2. **没有价格表。** 折算金额需要各模型的单价，且单价会变。OpenUsage 的做法是
   动态下载一份价格表。需要决定价格数据从哪来、多久更新、算错了怎么办。
3. **没有凭据授权流程。** 「用户批准后用其凭据调接口」需要一个明确的授权界面：
   逐个 Provider 询问、说明会发出什么请求、可随时撤销。不能默认开启。

#### 必须先确认：这推翻了一个已写进 README 的承诺

当前 `README.md` 的能力表里写着：**「优先显示真实 token；没有 token 时显示 Provider
quota、周期和重置时间，**不生成价格估算**。」** `docs/privacy-policy.md` 与
`RELEASING.md` 也建立在「基本只读本地、不外发凭据」这个定位上。

做额度结算 = 生成价格估算，并且会用用户凭据发起对外请求。
**这是产品定位的改变，不是功能增补。** 落地时必须同步更新 README 的能力表与
隐私说明，否则文档会和实际行为不符。

**待维护者确认**：知悉并接受上述定位改变？

#### 其余待明确

- 金额算出来是「估算」还是要求准确？各家计费规则（缓存命中折扣、批量折扣、
  套餐内不单独计费）差异很大，**按 token 乘单价得到的数字通常对不上真实账单**。
  建议在界面上明确标注为估算。
- 历史保留多久？（90 天？永久？）
- 统计口径按哪个时区、每天几点切分？

### F2. OpenUsage 方案对比 **[待研究]**

维护者了解到 OpenUsage 这个开源项目也做额度展示，主要支持 macOS，
Windows 有迁移方案。希望了解它与当前方案的异同，以及是否值得借鉴复用。

**已调研（2026-09-18）**，对象为 `robinebers/openusage`（Swift，macOS 15+，约 4.2k star）。
另有两个 Tauri 写的 Windows 移植（`mesomya/openusage-windows`、`Pusselz/openusage-windows`），
以及一个 Windows 原生同类 `ItsJazii/pane`（Rust）。

#### 取数方式的根本差异

| | OpenUsage | Vibe Board 当前 |
| --- | --- | --- |
| 主路径 | 复用机器上已有的凭据（keychain、auth 文件、App 状态），**用它去调 Provider 自己的用量/账单 API** | 以读本地文件为主：Codex 走本地 app-server 桥接取限额、失败回退读 rollout JSONL；其余多数读本地配置/状态文件 |
| 例外 | OpenRouter、Z.ai 无本地凭据，需用户填 API key | OpenCode 会读本地 API key 后调 `OPENCODE_GO_USAGE_URL` —— 这一条与 OpenUsage 同构 |
| 花费金额 | 本地 CLI 日志 × **动态下载的模型价格表**，给出今日/昨日/近 30 天花费 | **有意不做价格估算**（README 明确写「不生成价格估算」） |
| 覆盖 Provider | 11 个，含 Copilot、Cursor、Devin、Grok、Ollama、OpenRouter、Z.ai | 以本机可检测的编码 Agent 为主 |

**一句话**：OpenUsage 敢联网问 Provider 要数，所以拿到的维度多得多
（会话/周/模型级限额、credits、花费）；Vibe Board 基本只读本地，数据维度受限，
但不承担凭据外发的风险，也不需要维护价格表。**这是产品取向差异，不是技术优劣。**

#### 真正值得借鉴的三点（与取数方式无关）

1. **三段式 Provider 管线**：每个 Provider 拆成 Auth store（读已有凭据）→ Usage client
   （取数）→ Mapper（归一化成统一的 `ProviderSnapshot` / `MetricLine`）。因为所有
   Provider 都产出同样形状的数据，UI 完全不需要知道各家细节。
   **对照当前实现**：`commands/mod.rs` 里是 `codex_usage_provider_status`、
   `claude_usage_provider_status`、`opencode_usage_provider_status`…… 一个 Provider
   一个定制函数，没有共同抽象。这是 F1「看不懂」的结构性原因之一——
   每块数据的含义都是各写各的。
2. **统一的增量日志扫描器**：Claude / Codex / Grok / pi 共用一个 `IncrementalJSONLScanner`，
   按路径+大小+修改时间缓存解析结果，跨进程复用，分批读取并跳过超大记录防止爆内存。
   Vibe Board 目前只有 Codex 一条 rollout 聚合路径，要扩展到别的 Agent 时可以照这个做。
3. **本地 HTTP API + 一次性 CLI**：`127.0.0.1:6736/v1/limits` 对外提供归一化数据，
   CLI 与 HTTP 共用同一个序列化器。**注意它自己在文档里标注了隐私风险**：
   loopback 接口浏览器页面也读得到。

#### 三条可选路线（待决策）

- **A. 只借鉴架构**：引入三段式 Provider 抽象 + 统一快照格式，取数仍以本地为主。
  改动集中在后端重构，不改变隐私姿态。**风险最低。**
- **B. 架构 + 选择性联网**：在 A 的基础上，对部分 Provider 增加「复用本地凭据调
  官方 API」的可选开关，默认关闭。能拿到更丰富的限额数据。
  **需要先明确：拿用户已有凭据去调第三方 API，是否符合你对这个产品的隐私定位。**
- **C. 直接消费 OpenUsage**：不自己实现，检测本机是否跑着 OpenUsage（或其 Windows
  移植 / `chpock/openusage-cli` 这个 Rust 守护进程），有就读它的本地 REST 接口。
  **成本最低但引入外部依赖**，且 Windows 端的移植成熟度未评估。

**已决策（2026-09-19）：选路线 B（借鉴架构 + 用户授权后联网取数）。**
见 F1 的目标定义。落地顺序建议：
1. 先做三段式 Provider 抽象（路线 A 的部分），把现在一个 Provider 一个定制函数的
   写法收敛成统一快照格式 —— 这是后面一切的地基，也直接缓解「看不懂」。
2. 再加历史存储与结算。
3. 凭据授权与联网取数最后做，因为它对外发起请求，风险最高，且需要单独的授权界面。
